# Round 7 · Design 第二批：推迟与重编码，以及延迟的合法性判据

> 类型：轮次复盘 ｜ 范围：0284 / 0341 / 0381 / 0641 / 0895 / 1381（6 题，另 0362 / 0359 会员跳过）
> 标记：5 `[x]`（0895 / 0341 / 1381 / 0641 / 0284）、1 `[x/r]`（0381）

## 摘要

[Round 2](round-02-design.md) 收敛出的命题是"组合数据结构的核心是多结构同步不变量"。本轮在同一专题上前进了一层：当不变量已经能维护住，下一个问题是**如何让维护成本更低**。六题给出两条路径——把计算推迟到必须发生的那一刻，以及重新编码状态表示让昂贵操作变便宜。

但本轮最有价值的不是这两条路径本身，而是 0381 提供的**反例**：延迟删除在该题必须被否决。由此得到一条判据——**推迟是否合法，取决于它是否污染了另一条不变量**。0381 的四版返工同时贡献了本轮全部三条失败模式，占据了本轮一半以上的篇幅。

## 主线一：推迟计算——三种形态

三题各用一种方式把工作推迟到不得不做的时刻：

**0341（推迟展开）**：不提前展开整个嵌套结构，栈中保存的是"当前列表 + 当前索引"而非所有元素，需要时才继续向下展开。空间从 `O(N)` 降到 `O(D)`（最大嵌套深度）。配合 prefetch 维护 `next`，使 `hasNext()` 能直接返回结果。

**1381（推迟生效）**：`increment(k, val)` 不修改底部 `k` 个元素，只把增量记在 `inc[min(k-1, top)]`。`pop()` 时当前元素领走自己那份增量、把它继续下传、清空当前位置——三个操作因此都是 `O(1)`。清空这一步是必需的，否则数组位置复用时会被旧增量污染。

**0895（推迟到不必做）**：`freqStacks[f]` 记录的是元素达到频率 `f` 时的时间顺序，而不是"当前所有频率为 `f` 的元素集合"。弹出最高频元素后，它在较低频率栈中的历史记录**不需要任何更新**——那些记录本身就还原了正确的相对顺序。`maxFreq` 只需减一，因为频率每次只升降一层。

0895 这一条与 [Round 4](round-04-audit-r1-r12.md) 的"状态不能太强"同源：不维护"当前真值"，而是保留历史层，让正确答案从历史中自然浮现。区别在于 R4 的样本是历史上界够用时不必维护真实值，这里是历史顺序够用时不必维护当前集合。

## 主线二：重新编码状态表示

另一条路径不是推迟，而是换一种方式表示同一批信息，使昂贵操作变成便宜操作：

**1381 的差分对照**：主流的另一种实现只用一个数组——不让单个整数同时承担"原值"和"增量"两个职责，而是存相邻元素的差值，把区间加法转化为两处边界修改。笔记的总结点得很准：**信息没有减少，而是利用元素之间的相关性重新编码，降低了维护成本**。同题给出的选型结论同样值得保留：差分方案的状态表示思想值得学，但工程实现比双数组更难理解、更易写错，面试中双数组可读性更好。

**0641 的空槽**：环形结构中 `front == rear` 既可能是空也可能是满。永久预留一个空槽（容量取 `k + 1`）后，`front == rear` 表示空、`(front + 1) % capacity == rear` 表示满——**用一个槽位换掉了"元素计数"这个需要同步维护的状态**。这是本轮成本最低的一次重编码。

0641 同时是本轮唯一做了三版实现横向对比的题（固定环形双向链表 → 动态链表节点复用 → 环形数组），选型理由完整：容量在构造时已确定的固定容量双端队列，环形数组在操作复杂度、运行时分配、cache locality、状态复杂度四项上全面占优；动态链表的节点复用（删除时不真正释放、保留供后续插入）是一个独立可迁移的技巧，但在本题的固定容量前提下没有用武之地。

## 主线三：延迟的合法性判据（0381 否决延迟删除）

0381 要求 `getRandom()` 返回每个值的概率与它在集合中的出现次数严格成正比，因此 `ArrayList` 保存每一次出现几乎是锁定的设计——数组每个位置代表一次独立出现，在 `[0, size)` 均匀取下标即可自然满足比例要求。

随后要在 O(1) 内删除指定下标，第一个想法是延迟删除：不立刻修改数组，只把位置标记为已删除，后续插入时复用。**这个想法被否决了**，理由是它破坏了上面那条概率不变量：随机下标可能落到脏位置，从该位置向后找有效元素既不再是 O(1)，也改变了各元素被选中的概率，使概率不再与出现次数严格线性相关。最终改用交换尾删。

把它与 1381 并排看，本轮最重要的一条规则就出来了：

**延迟是否可用，不取决于它能省多少工作，而取决于系统中是否存在另一条会被它污染的不变量。** 1381 的延迟增量只影响"元素值何时生效"，而该结构没有任何操作依赖"底部元素此刻的真实值"，因此安全；0381 的延迟删除直接落在 `getRandom` 依赖的"数组中每个位置都是一次有效出现"上，因此不安全。动手前的检查动作是：**列出所有操作依赖的不变量，逐条对照延迟会不会让某一条失效。**

## 主线四：隐含不变量未显式化（0381 第一版）

第一版认为同一个值的下标是按插入顺序进入 List 的，因此 List 末尾一定是最大下标。初始状态确实成立——某值依次插入下标 2、5、8，列表就是 `[2, 5, 8]`。

但交换删除会破坏它：某值原本位于下标 4 和 5，列表为 `[4, 5]`；删除其他元素时把下标 5 的元素移到下标 3，列表被改成 `[4, 3]`。此时数组中更靠后的下标是 4，而 List 末尾是 3。**"List 的排列顺序代表下标大小"这条性质，在引入交换删除的那一刻就不再成立**，继续按末尾更新就会改错记录。

这是 [Round 2](round-02-design.md) "多结构同步不变量"的一个新变种：R2 的样本是两个结构之间的同步等式写错或顺序写反，这里是**根本没有把该性质当成一条需要维护的不变量**——它在初始状态下自动成立，因而从未被写下来，也就无人检查它是否被后续操作破坏。规则：**凡是"在当前实现下恰好成立"的性质，如果代码依赖它，就必须显式写下来并在每个修改点复查。**

## 主线五：把已知信息误当成需要查询的信息（0381 的思路死结）

修正上一条时，需求被表述成"一种能 O(1) 插入下标、并 O(1) 删除数组末尾下标的结构"。这句话被进一步误解成"能 O(1) 插入并 O(1) 删除最大值的结构"——一般数据结构做不到两者兼得，思路因此卡住。

实际上删除目标是**已经明确知道的**：`lastIdx = nums.size() - 1`。真正的需求只是"O(1) 插入一个已知下标 + O(1) 删除一个已知下标"，而同一个值的下标天然互不相同。`HashSet<Integer>` 即可满足，结构改为 `HashMap<Integer, Set<Integer>>` 后 List 的顺序问题被彻底消解。

这条失败模式可以独立命名：**把调用方已经持有的信息，误当成需要数据结构自己去找的信息，从而给结构提出了它本不必满足的要求。** 检查动作：写下需求后逐项标注"这个量是已知的还是需要查的"，只对真正需要查的部分挑结构。

这与 [Round 1](round-01-union-find.md) 的"工具语义边界"互补——那里是给工具派了它做不到的活，这里是给工具派了它根本不必做的活。

## 主线六：引用别名，调顺序解决不了（0381 第三、四版）

改用 Set 之后，交换删除的更新顺序又连错两版，根因相同：当待删值与数组末尾值相同（`val == lastNum`）时，`removeIdxs` 与 `lastIdxs` **是同一个 Set 对象**。

- 第三版顺序（删末尾下标 → 加移动后下标 → 删待删下标）：`nums = [1, 1]`、集合 `{0, 1}`、删下标 0 并把下标 1 移到 0，三步走完集合成空集，而数组尾删后仍留一个 `1`——数组与 Map 状态不一致。
- 第四版调换顺序后，`idx != lastIdx` 时正确；但 `HashSet.iterator().next()` 只保证取出任意元素，无法保证取到的不是 `lastIdx`。一旦取到 `lastIdx`，就会先删它、再删一次、最后又把这个已失效的下标加回集合。

**出路不是继续调整集合操作顺序，而是先判掉退化情形**：若 `nums.get(lastIdx) == val`，根本不需要交换，直接从该值的 Set 中删掉 `lastIdx`、再尾删数组即可。只有 `lastNum != val` 时才执行真正的交换删除，此时两个 Set 必然是不同对象，别名冲突不复存在。

可迁移规则：**当两个引用可能指向同一对象时，排列组合式地调整操作顺序是在有限空间内碰运气；正确做法是识别出别名成立的条件，把它作为独立分支提前处理掉。**

## 规则清单

1. 推迟计算前，列出所有操作依赖的不变量，逐条检查延迟会不会让某一条失效（1381 安全 / 0381 不安全）。
2. 延迟标记必须在生效后清空，否则位置复用时被旧值污染。
3. 保留历史层常比维护当前真值便宜：历史顺序若已足够还原答案，就不要回溯更新（0895）。
4. 昂贵操作先考虑换状态表示，而非优化操作本身（差分把区间加变成边界改；空槽换掉计数状态）。
5. 凡是"在当前实现下恰好成立"的性质，只要代码依赖它，就必须显式写下并在每个修改点复查。
6. 写下需求后逐项标注"已知 / 需查"，只为真正需要查的部分挑数据结构。
7. 两个引用可能指向同一对象时，不要靠调顺序绕开；把别名条件作为独立分支提前判掉。
8. 面试实现在等价方案间优先可读性（1381 双数组优于差分），选型理由写进笔记。
