# 460. LFU Cache（Review）

耗时：40min（超时）

## 我的思考

本次复刷耗时约 40min，超过目标时间（30min）。

和第一次不同，这次并没有忘记 LFU 的整体数据结构，很快确定仍然采用：

- `nodeMap`：维护 `key -> Node`
- `freqMap`：维护 `freq -> 哨兵节点`
- `Node`：维护 `key / val / freq / prev / next`
- `minFreq`：维护当前最小频率

真正耗时主要集中在实现细节，而不是算法思路。

主要犹豫点：

- 是否需要单独封装 `DoublyLinkedList`，最终认为不需要，`freqMap` 配合哨兵节点即可完成同样功能。
- `Node` 需要哪些字段：
  - `val`：需要，`get` 要返回值。
  - `key`：需要，删除节点时需要从 `nodeMap` 中移除。
  - `prev / next`：需要，支持 O(1) 摘链。
  - `freq`：需要，定位所属频率桶。
- 是否抽离辅助方法，以及抽离到什么粒度。

最终选择把 `nodeMap` 与 `freqMap` 的维护一起封装到 `deleteNode()` / `addNode()` 中，上层 `get` 和 `put` 只负责调用。

## 卡点

没有卡在算法设计。

主要耗时来自数据结构组织与接口职责设计，例如：

- 是否需要独立的 `DoublyLinkedList`。
- `Node` 应保存哪些信息。
- 底层辅助方法应该负责哪些职责。

另外，为了复用逻辑，更新已有节点时直接调用 `get(key)` 完成提频，这是一个有意识接受的实现取舍，但接口职责存在耦合。

## 关键点

LFU 的整体结构已经形成稳定记忆：

- `HashMap<key, Node>`
- `HashMap<freq, bucket>`
- `Node(key, val, freq, prev, next)`
- `minFreq`

本次再次验证了 `minFreq` 的维护规律：

- 提频导致最小频率桶清空时，`minFreq++`。
- 插入新节点时，`minFreq` 重置为 `1`。

## 主流解对照

本次没有采用第一次的 `DoublyLinkedList` 封装，而是直接使用频率哨兵节点代替频率桶对象。

实现思路本质等价，只是进一步减少了数据结构数量。

不过接口职责划分仍然偏粗。

目前：

- `deleteNode()` 同时负责链表维护、`nodeMap`、`freqMap`、`minFreq`
- `addNode()` 同时负责链表维护、`nodeMap`、`minFreq`

更清晰的划分应类似于：

- `unlink(node)`：仅负责从频率链表摘除节点。
- `addFirst(node)`：仅负责加入目标频率链表。
- `increaseFreq(node)`：完成一次访问导致的提频。
- `evict()`：负责真正淘汰节点，并同步维护 `nodeMap`。

这样可以避免 `put()` 借助 `get()` 的副作用完成提频，使各接口职责更加单一。

## 复杂度

- `get`：O(1)
- `put`：O(1)
- 空间复杂度：O(capacity)

## 注意

- `put` 不应长期依赖 `get` 的副作用完成提频，否则接口语义容易耦合。
- 底层辅助方法应尽量保持单一职责，避免同时维护链表、Map 和 `minFreq`，降低推理复杂度。

  - 不再犹豫 `Node` 字段设计。
  - 独立实现 `increaseFreq()`，取消 `put -> get` 的复用方式。
