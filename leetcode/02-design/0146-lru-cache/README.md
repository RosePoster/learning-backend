# 146. LRU Cache

## 我的思考（仅润色语序和表述，不增减内容）

一开始想到使用一个 queue 来实现先入先出。

为了处理 `1, 0, 1` 这种同一个 key 被重复访问的情况，尝试使用一个计数器记录队列里某个 key 出现了几次。

当 cache 满了以后，开始执行删除流程：

如果当前队头元素在计数器里的值大于 1，说明它不是当前有效的最久未使用元素，只需要将计数器减 1，并继续向后删除。

如果计数器里的值为 1，说明当前元素就是需要删除的元素，删除并结束流程。

在 `get` 或 `put` 时，只是简单将 key 入队，并让计数器对应值加 1。

但这个方案是 lazy delete，淘汰时可能要连续删除多个过期访问记录，最坏时间复杂度是 `O(n)`，不能满足题目要求。

随后意识到关键问题是：访问队列中的已有元素时，需要能够将它提到队头。普通队列无法在 `O(1)` 时间访问和移动中间元素。

尝试过双队列方案：访问队列中的元素时，将队头元素不断从后插入新队列，直到找到访问的元素，将此元素从前插入新队列，然后剩余元素继续从后插入。但这样每次插入和删除都是 `O(capacity)`，复杂度更差。

最终采用双向链表 + HashMap 的结构：

- 双向链表维护最近使用顺序。
- HashMap 的 key 存缓存 key，value 存链表节点引用。
- `get` 时根据 key 找到对应节点，取出 value，并将节点移动到队头。
- `put` 时，如果 key 已存在，更新节点 value，并移动到队头。
- 如果 key 不存在，新增节点并插入队头。
- 当超过容量时，删除链表尾部节点，并同步删除 map 中对应 key。

## 卡点

1. 没能自己想到 `Map` 的 value 可以直接存储链表节点引用。

这是 LRU Cache 的公认解法，需要记住：

`HashMap` 负责根据 key 在 `O(1)` 时间定位节点；双向链表负责在 `O(1)` 时间删除节点、移动节点和淘汰尾部节点。

2. 一开始忘记在 node 中存储 key，导致删除尾部节点时无法正确删除 map 中的元素。

这个错误的本质是没有严格区分清楚 `key` 和 `val`。

删除尾部节点这一步的方向是：

从链表尾部节点 `node` 找到它对应的 `key`，再用这个 `key` 删除 map 中的记录。

但 map 只提供 `key -> node` 的映射，不提供 `node -> key` 的反向查找能力。因此，链表节点中必须额外保存 `key`。

## 关键点

- LRU 的核心不是 FIFO，而是最近使用顺序。
- 每次 `get` 命中后，也算一次使用，需要将节点移动到最近使用位置。
- 每次 `put` 已存在 key 时，需要更新 value，并将节点移动到最近使用位置。
- 淘汰时删除的是最久未使用节点，通常放在链表尾部。
- 双向链表相比单向链表的关键优势是：已知节点引用时，可以在 `O(1)` 时间删除该节点。
- `HashMap<Integer, Node>` 的 value 存的是节点引用，而不是节点值。
- Node 中必须同时保存 `key` 和 `val`：
  - `val` 用于 `get` 返回。
  - `key` 用于淘汰尾部节点时删除 map 中对应记录。
- dummy head / dummy tail 可以避免删除头尾节点时的大量边界判断。

## 主流解对照

一致

## 复杂度

- 时间：`get` 和 `put` 均为 `O(1)` 平均时间复杂度。
- 空间：`O(capacity)`。

## 注意

- `Map` 的 value 可以存储对象引用，例如链表节点本身。
- 不要把 `key` 和 `val` 混淆：
  - `key` 是 cache 的索引，也是 map 删除时需要的标识。
  - `val` 是用户通过 `get(key)` 想要获得的数据。
- 使用 map.size()记录 len 可以减少状态同步风险。
- Node 可以定义为 private static class Node，字段不必使用 public。
