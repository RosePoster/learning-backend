# 399. Evaluate Division

## 我的思考
本题将每个变量视为图中的节点，将等式视为带权有向边。对于 `a / b = value`，建立 `a -> b`，边权为 `value`；同时建立反向边 `b -> a`，边权为 `1 / value`。

查询时，从 `start` 出发 DFS 搜索 `end`。搜索过程中维护当前路径上的累乘值 `dist`，当到达 `end` 时，当前 `dist` 即为答案。若 `start` 或 `end` 不存在于图中，则直接返回 `-1.0`。

本题一开始曾误解为变量字符串可以拆解，例如以为 `"ab"` 可以拆成 `"a" * "b"`。后来明确：题目中的变量是完整字符串，`"ab"` 与 `"a"`、`"b"` 没有任何自动关系。

进一步思考时，最开始想到的是把每个节点可以到达的所有终点与距离都缓存到 graph 中。例如对于：

    a -> b = 0.5
    b -> c = 0.5
    c -> d = 0.5

可以得到：

    a: b(0.5), c(0.25), d(0.125)
    b: a(2), c(0.5), d(0.25)
    c: a(4), b(2), d(0.5)

因为直连边和间接推导出的比例边，在查询语义上是等价的。但如果预处理所有可达关系，代价会比较大。因此可以使用lazy记忆化，在count遍历中动态记忆，但为了实现效率当前代码先实现了普通 DFS，没有加入记忆化。

后续可在 DFS 内做 lazy 记忆化：当一次搜索找到 `end` 后，将这条搜索路径上从 `start` 到中间节点的比例关系增量加入 graph。这样可以逐步缓存被查询过的子图，而不是一开始构造全闭包。

## 卡点
- 一开始误解题意，以为变量字符串可以拆解；实际 `"ab"` 是完整变量名，不等于 `"a" * "b"`。
- 记忆化如果使用 `Set<Edge>`，需要注意 `record Edge(String to, double dist)` 的默认 equality 会同时包含 `to` 和 `dist`，不符合“按目标节点去重”的语义。
- 若要做缓存，更合适的数据结构是 `Map<Integer, Double>` 或 `Map<String, Double>`，按目标节点作为语义 key 去重。

## 关键点
- 带权图建模：边权为比值，反向边取倒数，路径累乘。
- `visited` 不回溯：题目隐含保证方程组无矛盾，即图内任意环权值积为 1，因此同一连通分量内任意路径得到的比例一致，只需要找到任意一条路径。
- 查询前先判断 `start` 和 `end` 是否存在；如果任一变量不存在，答案为 `-1.0`。
- 当 `start.equals(end)` 且变量存在时，答案为 `1.0`。
- 直连边和间接连接边在查询语义上等价，区别只是预处理还是 lazy 缓存。

### 两种工程化优化方向（未实现）
1. lazy 记忆化 + 路径压缩：DFS 找到 `end` 后，沿路径把 `(start, 路径上每个节点)` 增量加入 graph。
   - 收敛到“被查询过的子图”，避免预处理全闭包。
   - cache 应使用 `Map<Integer, Double>` 或 `Map<String, Double>`，而不是 `Set<Edge>`，按“语义 key”去重。
   - 适用场景：query 高度重复、start 节点集中。

2. 加权并查集：维护 `node -> root` 的权值比，union 时按权值对齐。
   - 预处理 `O(E * α)`，单次 query `O(α)`。
   - 适用场景：query 量远大于 equation 量。

## 主流解对照
LeetCode 主流做法包括带权图 DFS/BFS、Floyd 传递闭包、加权并查集。当前解法属于带权图 DFS，与主流解法等价；未实现的 lazy 记忆化属于在 DFS 基础上的工程化缓存优化。

## 复杂度
- 建图时间：`O(E)`，其中 `E` 为 equations 数量。
- 单次查询时间：`O(V + E)`，其中 `V` 为变量数量。
- 总时间：`O(E + Q * (V + E))`，其中 `Q` 为 queries 数量。
- 空间：`O(V + E)`。

## 注意
- 当前代码是普通 DFS 版本，结构简单、足够稳定。
