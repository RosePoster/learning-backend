# 721. 账户合并

## 我的思考（仅润色语序和表述，不增减内容）

这题的核心是把邮箱之间的共享关系建模为连通关系。每个 email 可以看作一个节点，同一个 account 中出现的所有 email 属于同一个连通分量。最终需要把属于同一连通分量的邮箱合并，并按字典序排序后输出。

最初写法是先建立 email 到编号的映射，再用 Union-Find 合并同一个账户内的邮箱。合并完成后，遍历所有邮箱编号，根据最终 root 聚合邮箱，再为每个 root 找到对应的 name，最后排序并组织答案。

写到一半时，尝试过另一种在线构建答案的思路：认为 Union-Find 的深度似乎只需要为 1，可以在扫描 accounts 的过程中一边确定邮箱归属，一边构造 mergedAccounts。这个想法后来被反例推翻。

反例：

a: 1, 2  
a: 3, 4  
a: 2, 3  

在线构建答案时，会先把 1,2 和 3,4 划分成两个账户。等扫描到 2,3 时，才发现这两个已有账户应该合并，但此时答案结构已经提前物化，后续合并会失效或变得很麻烦。

因此，这题不能边构建 Union-Find 边生成最终答案。应该先处理完所有等价关系，再根据最终 root 聚合邮箱。

## 卡点

中途尝试把 union 阶段和答案构造阶段合并，导致思路走偏。问题本质是：721 的合并关系具有传递性，后续输入可能把两个已经存在的 group 再次合并，因此答案 group 不能提前定型。

另外，代码中为了结构化写了 Translator 类，在 LeetCode 限时场景下，过度封装会增加额外的低级错误风险。

## 关键点

这题是典型的等价关系合并问题。邮箱是节点，同一账户内的邮箱之间存在等价关系。多个账户通过共享邮箱连接后，属于同一个连通分量。

正确流程应该分成两个阶段：

1. Union 阶段：只负责建立 email 编号，并合并同一账户内的 email。
2. Collect 阶段：所有 union 完成后，再按照最终 root 聚合 email，排序并补上 name。

可以边扫描边分配 email id，也可以边扫描边 union，但不能边扫描边物化最终答案。

对于同一个 account 内的邮箱，既可以相邻两两 union，也可以固定第一个邮箱，让其他邮箱都和第一个邮箱 union。两种方式都正确，但固定第一个邮箱更容易解释。

在 Java 实现上，UnionFind 值得单独抽类，因为它有独立的不变量和标准操作。但 Translator 这种薄封装收益不高，直接使用：

Map<String, Integer> emailToId  
List<String> idToEmail  

通常更低风险。List 天然支持 id 到 email 的反向映射。

## 主流解对照

主流做法是将每个 email 离散化为编号，使用 Union-Find 合并同一账户内的邮箱。所有合并完成后，遍历所有 email，根据最终 root 分组，再对每组邮箱排序，并在开头加入账户名。用户最终解法与主流 Union-Find 解法等价，但结构略偏工程化；中途尝试的在线构造答案模型不适合这类传递等价关系问题。

## 复杂度

时间：O(E α(E) + E log E)，其中 E 是所有邮箱出现次数或去重后的邮箱数量级。Union-Find 操作近似常数，主要开销来自最终对每组邮箱排序。整体也可以视为 O(E log E)。

空间：O(E)，用于 email 映射、Union-Find parent 数组、root 到邮箱列表的聚合结构。

## 注意

如果输入描述的是一批具有传递性的等价关系，不要提前生成答案 group。先处理完所有 union，再按最终 root 收集。

这题暴露的问题不是不会并查集，而是写到一半想探索更“在线”的实现，导致实现路径被拖慢。面试中一旦识别为 equivalence classes / connected components，并且已经选择 Union-Find，就应避免再尝试同时维护最终答案。
