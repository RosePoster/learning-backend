耗时：50min
这题首先需要实现 `getRandom()`，并且每个值被返回的概率必须与它在集合中的出现次数严格成正比。

因此，使用 `ArrayList` 存储所有元素几乎是一个锁定的设计。数组中的每个位置都代表一次独立出现，只要在 `[0, nums.size())` 中均匀随机一个下标，就能自然保证某个值出现多少次，它被随机到的概率就有多少份。

同时，`ArrayList` 支持尾部插入，单次插入的摊还时间复杂度为 O(1)。

最初考虑使用一个 `HashMap<Integer, Integer> counter` 记录每个值出现的次数。这样插入时可以判断该值此前是否存在：只有原计数为 0 时，`insert` 才返回 `true`，否则返回 `false`。

但继续考虑删除操作后发现，仅记录数量不够。

题目要求按照值在 O(1) 时间内删除一个元素，而真正存储元素的是 `nums`。要删除指定值，就必须知道这个值在 `nums` 中的某个下标。因此，将原来的计数结构进一步改造为：

`HashMap<Integer, List<Integer>> num2idx`

其中，每个值映射到它在 `nums` 中出现过的全部下标。

接下来需要解决如何从 `ArrayList` 中 O(1) 删除指定下标的问题。

一种想法是延迟删除：不立刻修改数组，只将这个位置标记为已经删除，之后插入新元素时再复用这些位置。

但这种方法会破坏 `getRandom()`。随机下标可能落到已经删除的脏位置上。虽然可以从该位置继续向后寻找有效元素，但这样不仅无法保证 O(1) 时间复杂度，也会改变不同元素被选中的概率，使概率不再与出现次数严格线性相关。因此不能使用延迟删除。

另一种方法是交换删除：

1. 找到待删除元素的下标 `idx`。
2. 将数组末尾元素移动到 `idx`。
3. 删除数组末尾。

这样只进行常数次随机访问和尾删，可以在 O(1) 时间内完成数组删除。

第一版实现中，认为同一个值的下标是按照插入顺序加入 List 的，因此越靠后的下标一定越大。于是删除数组末尾元素时，直接修改它对应下标 List 的最后一个位置。

初始状态下，这个判断确实成立。例如某个值依次插入到下标 2、5、8，那么它的下标列表为：

`[2, 5, 8]`

最后一个下标就是最大下标。

但一旦发生交换删除，这个性质就会被破坏。

例如某个值原本位于下标 4 和 5：

`[4, 5]`

删除其他元素时，可能将下标 5 的元素移动到下标 3，于是下标列表被修改为：

`[4, 3]`

此时数组中更靠后的下标是 4，但 List 的末尾却是 3。

因此，List 中元素的排列顺序不再代表下标大小。继续直接修改 List 的末尾，就可能更新错误的下标记录。

第二版主要调整了同一个 List 被同时作为待删除值列表和末尾值列表时的操作顺序，并且在下标列表为空后删除 Map 中的键，但它仍然没有解决“List 末尾不一定对应数组末尾下标”这个根本问题。

为了修正这一点，我开始寻找一种能够同时支持：

- O(1) 插入下标；
- O(1) 删除数组末尾下标。

一开始，我把这个需求误解成了“需要一种能够 O(1) 插入并 O(1) 删除最大值的数据结构”。

对于一般的数据结构，这两个操作通常无法同时做到 O(1)，因此思路一度卡在这里。

但实际上，这里并不需要数据结构自己寻找最大值。需要删除的下标是已经明确知道的：

`lastIdx = nums.size() - 1`

所以真正的需求只是：

- O(1) 插入一个已知下标；
- O(1) 删除一个已知下标。

而且同一个值对应的下标天然互不相同。

因此可以直接使用 `HashSet<Integer>`，将结构改为：

`HashMap<Integer, Set<Integer>> num2idx`

HashSet 平均 O(1) 支持：

- 加入新下标；
- 删除指定的 `lastIdx`；
- 任意取出一个待删除下标。

到这里，List 的顺序问题被彻底解决。

但交换逻辑中又出现了新的坑：待删除值可能与数组末尾值相同。

第三版的更新顺序是：

1. 从末尾值的 Set 中删除 `lastIdx`。
2. 将移动后的下标 `idx` 加入末尾值的 Set。
3. 从待删除值的 Set 中删除 `idx`。

当 `val == lastNum` 时，`removeIdxs` 和 `lastIdxs` 实际上指向同一个 Set。

例如：

`nums = [1, 1]`

下标集合为：

`1 -> {0, 1}`

假设准备删除下标 0，并将下标 1 的元素移动到下标 0。

按照第三版的顺序：

- 删除下标 1，集合变成 `{0}`；
- 加入下标 0，集合仍然是 `{0}`；
- 删除下标 0，集合变成空集。

但数组删除末尾后仍然保留一个 `1`，于是数组和 Map 的状态不一致。

第四版尝试通过调整操作顺序解决这个问题：

1. 先从待删除值的 Set 中删除 `idx`。
2. 再从末尾值的 Set 中删除 `lastIdx`。
3. 将 `idx` 加入末尾值的 Set。

当 `idx != lastIdx` 时，这个顺序可以正确表达“删除位于 idx 的元素，再把位于 lastIdx 的同值元素移动到 idx”。

但如果任意取出的 `idx` 恰好就是 `lastIdx`，就会出现新的问题：

- 先删除 `lastIdx`；
- 随后再次尝试删除 `lastIdx`；
- 最后又将这个已经失效的下标加入 Set。

数组末尾已经被删除，但 Set 中重新出现了这个下标。

由于 `HashSet.iterator().next()` 只能保证取出任意元素，无法保证它不是 `lastIdx`，因此不能依赖这种更新顺序规避问题。

最终发现，最干净的处理方式不是继续调整集合操作顺序，而是先判断数组末尾本身是不是待删除值。

如果：

`nums.get(lastIdx) == val`

那么根本不需要交换。

直接：

1. 从 `val` 对应的 Set 中删除 `lastIdx`。
2. 删除 `nums` 的末尾元素。

这样既不会移动任何元素，也不会涉及同一个 Set 的交叉更新。

只有当：

`lastNum != val`

时，才需要真正执行交换删除：

1. 从待删除值的 Set 中任取一个下标 `idx`。
2. 从末尾值的 Set 中删除 `lastIdx`。
3. 将 `idx` 加入末尾值的 Set。
4. 在 `nums[idx]` 中写入末尾值。
5. 从待删除值的 Set 中删除 `idx`。
6. 删除数组末尾。

此时 `lastNum` 与 `val` 不同，两个 Set 必然是不同对象，不再存在引用别名导致的更新冲突。

整个思路最终形成了三个核心结构关系：

- `ArrayList` 保存每一次元素出现，保证随机概率与出现次数严格成正比。
- `HashMap` 根据值找到该值所有出现位置。
- `HashSet` 支持 O(1) 插入、删除和任取一个下标。

删除时使用交换尾删，并对“末尾元素正好就是待删除值”的情况直接尾删，从而避免不必要的交换和同一 Set 的引用冲突。
