## 我的思考

本题状态设计比较直接：

定义：
- `states[i]` 表示到达第 `i` 块石头时，当前可以使用的跳跃长度集合。

因为下一次跳跃长度只依赖于当前跳跃长度：
- 下一步可以跳 `k - 1`
- `k`
- `k + 1`

因此记录每个石头对应的可达 jump length 即可。

初始化：
- 第一块石头固定为 0
- 第二块石头只有在距离为 1 时才能到达，因此初始状态为 `states[1] = {1}`。

遍历每个石头的状态：
- 对每个已有 jump length，向后寻找距离满足：
  - `stepLen - 1`
  - `stepLen`
  - `stepLen + 1`
  的下一块石头。
- 找到后，将实际跳跃距离加入目标石头状态。

处理完成后的石头状态不再需要，因此删除，减少空间占用。

## 卡点

无明显卡点。

完成基础状态转移后，进一步考虑了转移优化：

当前实现：

```
state -> 查找目标石头
```

即遍历已有 jump length，再扫描后续石头。

优化方向：

反转为：

```
目标石头 -> 判断是否存在对应jump length
```

对于距离 `len` 的下一块石头，只需要检查：

```
len - 1
len
len + 1
```

是否存在于当前状态集合中。

进一步利用石头位置的 hash set，可以直接判断：

```
当前位置 + jump - 1
当前位置 + jump
当前位置 + jump + 1
```

是否存在石头。

---

## 关键点

本题核心不是传统 DP 表，而是建立稀疏状态空间。

状态：

```
石头位置 -> 可达跳跃长度集合
```

相比记录所有位置转移，状态数量大幅减少。

状态转移：

```
当前位置 + 当前jump
    ↓
下一跳长度 = jump ± 1
    ↓
更新目标石头状态
```

最终答案只需要判断最后一块石头是否存在可达状态。

---

## 主流解对照

标准优化解：

使用：

```
stone position -> index
```

建立 hash 映射。

遍历每个状态：

```
(current stone, jump)
```

直接检查：

```
position + jump - 1
position + jump
position + jump + 1
```

是否存在石头。

复杂度：

相比当前实现减少了寻找目标石头的扫描过程。

---

## 复杂度

当前实现：

时间复杂度：

```
O(n^3)
```

状态数量：

```
O(n^2)
```

每个状态最坏需要扫描后续石头。

空间复杂度：

```
O(n^2)
```

优化后：

时间复杂度：

```
O(n^2)
```

空间复杂度：

```
O(n^2)
```

---

## 注意

- 状态数量不是 O(n)，因为同一块石头可能由多个 jump length 到达。
- 不能只记录是否到达某块石头，否则会丢失后续跳跃信息。
- `k ± 1` 的限制决定了状态维度必须包含当前跳跃长度。
- 当前实现利用了 stones 有序这一性质，通过提前 break 减少实际扫描。
- `states.remove(i)` 是有效空间优化，因为已经处理过的状态不会再次被使用。
