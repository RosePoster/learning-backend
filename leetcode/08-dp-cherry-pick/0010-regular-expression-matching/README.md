## 我的思考
定义 `dp[i][j]`：`p` 的前 `j` 个字符能否完整匹配 `s` 的前 `i` 个字符。

普通字符或 `.` 的匹配是确定的，只需要依赖左上角状态：

`dp[i][j] = dp[i - 1][j - 1] && match(s[i], p[j])`

真正引入复杂状态的是 `*`。

这里将 `*` 视为前一个字符的修饰符，而不是独立的匹配单元。对于形如 `x*` 的结构，只需要考虑：

- 不使用：继承当前行左侧状态。
- 多使用一次：如果 `x` 能匹配当前字符，则继承上一行当前 `x*` 对应的状态。

“多使用一次”可以反复发生，因此自然覆盖使用任意 `n` 次的情况。

实现时压缩为一维 `dp`：

- `up`：更新前的 `dp[j]`，即上一行当前状态。
- `pre`：上一行前一个真实匹配状态。
- `dp[j - 1]`：当前行已经更新完成的左侧状态。

`*` 本身只是前一个真实状态的影子，因此遇到 `*` 时只同步：

`dp[j] = dp[j - 1]`

并且不更新 `pre`。

## 卡点
第一次实现时虽然已经确定使用 DP，但没有完全理清 `*` 对状态转移的影响，尤其是如何表达 `x*` 连续消费多个字符。

最初试图用“使用 0 次 / 使用 1 次”描述 `*`，后来明确：只要“使用 1 次”后的状态仍然保留 `x*` 的继续使用能力，就可以通过重复该转移表达使用任意多次。

另外需要处理 pattern 前缀由若干 `x*` 组成时可以匹配空串的初始化。

## 关键点
`*` 不是独立匹配单位，而是前一个字符的 modifier。

对于真实 pattern 字符 `p[j]`：

- 若后面没有 `*`：
  `dp[j] = pre && match`

- 若后面存在 `*`：
  `dp[j] = (up && match) || dp[j - 1]`

其中：

- `up && match`：`x*` 再消费一个当前字符。
- `dp[j - 1]`：本次不使用 `x*`。

初始化时，连续的 `x*` 前缀均可以通过使用 0 次匹配空串。

进一步观察：当 pattern 不含 `*` 时，本题本质只是 O(n) 的线性匹配，DP 的额外开销完全来自 `*` 引起的状态扩散。

因此理论上可以进一步做自适应优化：

- 当前只有一个 reachable state 时，直接进行 forced linear matching。
- 遇到 `*` 导致状态扩散时切回 DP。
- DP 再次收敛到唯一 reachable state 后重新退化为线性匹配。

该优化不改变最坏 O(nm) 复杂度，但对于大量确定性匹配区间可以明显减少无意义的 DP 扫描。该思想与 LC97 中使用过的“状态扩散 → DP，状态收敛 → forced phase”一致。

## 主流解对照
主流解通常直接定义二维 DP，并将 `x*` 作为一个整体写出：

- 使用 0 次 `x`
- 使用至少 1 次 `x`

本解本质上仍是相同的 DP 状态转移，但进一步压缩到一维，并在实现层面认为 `*` 不作为独立匹配状态，仅作为前一个字符的修饰信息。

## 复杂度
时间复杂度：O(nm)

空间复杂度：O(m)

其中 `n = s.length()`，`m = p.length()`。

若进一步实现“singleton frontier 线性推进 + 状态扩散时 DP”的自适应版本，最坏仍为 O(nm)，但确定性区间可以接近线性处理。

## 注意
- `*` 不独立出现，可基于题目保证进行实现。
- `*` 不应更新 `pre`，因为它与真实匹配状态不在同一抽象层。
- `dp[j]` 被覆盖前必须保存为 `up`，供当前行转移使用。
- pattern 开头连续的 `x*` 可以全部使用 0 次，因此能够匹配空串，需要提前初始化。
- 一维压缩后的代码较依赖 invariant，面试时应能明确解释 `pre`、`up` 和当前行 `dp[j - 1]` 分别代表什么。
