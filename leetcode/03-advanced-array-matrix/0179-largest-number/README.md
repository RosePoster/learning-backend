# 179. Largest Number

## 我的思考
一开始没有直接想到 `a + b` 和 `b + a` 的比较方式，而是尝试给每个数构造一个独立优先级。

思路是先按首位分桶，桶间从 9 到 0 选择；桶内再把较短的数按自身规律补位到最长长度，然后按补位后的结果排序。

这个思路的直觉是：为了让最终数字最大，应当让更大的数字位尽可能靠前；由于每个数不能拆分，所以需要比较每个完整数字作为整体时的优先级。

但这个补位法有隐蔽缺陷：它试图给每个数计算一个固定的独立排序 key，而本题中两个数的相对顺序取决于它们互相拼接后的结果。

## 卡点
卡点在于：没有及时意识到这题不能用“单元素优先级”解决。

例如：

`830` 和 `8308`

补位后可能认为二者等价，但真实拼接结果是：

`8308308`

`8308830`

显然后者更大，所以 `8308` 应该排在 `830` 前面。

这说明短数补出来的虚拟后缀，不能代替真实拼接时后面接上的那个数。

## 关键点
本题的排序依据不是数字自身大小，也不是补位后的单元素 key，而是两个数的相对顺序。

对任意两个字符串数字 `a` 和 `b`，只有两种排列：

`a + b`

`b + a`

如果 `a + b > b + a`，则 `a` 应排在 `b` 前面；否则 `b` 应排在 `a` 前面。

Java 中可以写成降序比较器：

`(b + a).compareTo(a + b)`

## 主流解对照
我的补位分桶思路不是主流解，并且存在反例。

主流解法是把所有数字转成字符串，然后按 `(a + b)` 与 `(b + a)` 的结果排序。这个比较器直接服务于最终拼接结果，而不是为单个元素构造近似优先级。

## 复杂度
时间复杂度：O(n log n * k)，其中 k 是字符串拼接比较的长度量级。

空间复杂度：O(n * k)

## 注意
这题最有价值的 insight 是：

有些排序问题不存在可靠的单元素 key，必须用 pairwise comparator。

不要问“这个数本身的优先级是多少”，而要问：

“a 放在 b 前面更大，还是 b 放在 a 前面更大？”
