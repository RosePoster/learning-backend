# 2398. Maximum Number of Robots Within Budget

## 我的思考
一开始没有注意到题目要求选择的是**连续**的一段机器人，而误以为可以任意挑选，因此一直在思考如何从所有机器人中选择满足预算的集合。

意识到必须连续后，问题立刻转化为滑动窗口。因为窗口越大，`runningCosts` 总和和窗口长度都不会减小，窗口是否合法具有单调性，可以直接滑动窗口维护。

第一版使用大根堆维护窗口最大 `chargeTime`，配合 `HashMap` 做懒删除。

随后继续思考窗口最大值是否还能优化，改为提前预处理 `nextGreater`，维护窗口最大值下标，仅在当前最大值离开窗口时重新寻找新的最大值。

## 卡点
最大的卡点是读题错误。

由于一开始没有注意到必须连续选择，错误建模为任意挑选机器人，导致前约 10 分钟都在错误方向思考。

第二个卡点是窗口最大值维护。

第一版使用优先队列能够解决，但希望进一步优化。

第一次 `nextGreater` 版本存在问题：当 `chargeTimes` 全相等时，会不断沿着 `nextGreater` 链重复扫描，最坏退化为 `O(n²)`。

立刻意识到问题在于维护的是最大值，而不是最大值下标。

修正为维护**最新出现的最大值下标**：

- 新元素大于等于当前最大值时直接更新最大值下标；
- 只有当前最大值真正离开窗口时，才沿 `nextGreater` 链重新寻找窗口最大值。

这样最大值下标始终单调向右移动，不再出现重复扫描。

## 关键点
看到题目要求选择连续区间时，应立即转化为滑动窗口，而不是集合选择问题。

维护窗口最大值时，可以维护最大值下标，而不是最大值本身。

使用 `nextGreater` 时，要保证搜索起点全局单调向右移动，否则相等元素可能导致重复遍历，退化到 `O(n²)`。

## 主流解对照
主流解法使用单调队列维护窗口最大值。

本题最终实现使用的是 `nextGreater + 最大值下标` 的变体，同样可以做到 `O(n)`，但证明和实现都比单调队列更复杂。

## 复杂度
时间复杂度：`O(n)`

空间复杂度：`O(n)`

## 注意
第一版大根堆方案时间复杂度为 `O(n log n)`。

`nextGreater` 版本不要只维护最大值，必须维护最大值下标，否则相等元素会导致重复沿链扫描。
