# 321. Create Maximum Number

## 我的思考
一开始想到贪心：当前位尽可能选最大数字，因为字典序下 `900 > 899`，当前位更大不会被后续位弥补。

最初尝试在 `nums1` 和 `nums2` 中交错选择当前可达最大值，并用剩余可跳过数量控制能否跳到更大的位置。但很快发现这个思路在一些例子中会看不到后面更优的数字。

随后尝试用 `nextGreater` 预处理每个位置右侧下一个更大值，并在每次选择时基于剩余可跳过数量跳到当前可达的更大位置。

这个方向在非相等情况下可以推进，但遇到两个候选值相等时变得复杂。相等时不能只看后一位，也不能只用局部规则决定选哪一边；最坏情况下必须继续展开后续选择，比较两个子状态的最优结果。

第一天耗时约 1h，没有写出完整可提交版本。

第二天重新思考后，意识到一直平局的情况可以在 `j = 0` 时退化为直接比较两个后缀的字典序；而将 `j > 0` 的情况转化为 `j = 0` 的方法，是先枚举 `nums1` 和 `nums2` 分别取多少个数。

于是改为：枚举 `nums1` 取 `i` 个，`nums2` 取 `k - i` 个；分别构造两个数组中指定长度的最大子序列，再对两个固定子序列进行字典序合并。第二天改造耗时约 38min。

## 卡点
最主要的卡点是相等候选值的处理。

当 `nums1` 和 `nums2` 当前可选出的最大值相等时，无法通过“看下一位”或“谁损失大数字更少”这类局部规则稳定决定。因为真正需要比较的是：分别选择两边当前值后，两个子状态能构造出的最优后续序列谁更大。

如果在原始交错选择模型中递归展开这个比较，会出现状态爆炸。最坏情况下，很多位置都平局，每次平局都会继续展开两个子状态；不加记忆化可能指数级，加记忆化则状态接近 `(i1, i2, 已选个数)`，规模过大，且每个状态还涉及序列比较。

另一个卡点是，最开始把“当前位取最大”的贪心判断和“两个数组之间如何分配取数数量”揉在了一起，导致删除预算、平局比较、后续最优性都交织在同一个在线过程里，难以收敛到稳定实现。

## 关键点
这题不能把所有决策都塞进一个在线交错贪心里处理。平局时本质上是在比较两个子状态的最优解，直接递归展开会爆炸。

稳定转化是：

先枚举两个数组的取数数量，让 `nums1` 固定取 `i` 个，`nums2` 固定取 `k - i` 个。这样删除预算在单数组内部提前消化，进入合并阶段时，两个候选序列都已经固定，相等时只需要比较两个后缀的字典序。

也就是：

`枚举分配 -> 单数组最大子序列 -> 后缀字典序合并`

这样可以把原本 `j > 0` 时复杂的平局比较，转化为固定序列之间的 `j = 0` 后缀比较。

单数组构造最大子序列时，可以用 `nextGreater` 预处理作为个人变体：如果跳到下一个更大的位置后，剩余长度仍然足够，就跳过去。这个思路和第一天的推导有连续性。

但需要注意，`nextGreater` 预处理不是严格优于标准 `drop` 单调栈写法。它可能在某些输入上减少操作，但复杂度阶没有降低，证明和解释成本更高。面试或追求稳妥时，标准 `drop` 写法更容易说明。

## 主流解对照
主流解法是枚举两个数组分别取多少个数，然后用单调栈从单个数组中取指定长度的最大子序列，最后按后缀字典序合并两个子序列。

我的第二天版本整体已经转向这个框架，但在单数组最大子序列部分使用的是 `nextGreater` 预处理变体，而不是主流的 `drop` 单调栈写法。

## 复杂度
设 `n = nums1.length`，`m = nums2.length`。

枚举取数分配最多 `O(k)` 种。

每次构造两个子序列和合并结果。合并时如果反复遇到长相等前缀，后缀比较可能带来额外开销。

整体复杂度不是严格线性，属于可接受但实现和分析都偏重的一类解法。
