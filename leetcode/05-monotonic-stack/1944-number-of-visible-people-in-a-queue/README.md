# 1944. Number of Visible People in a Queue

## 我的思考
一开始的想法是：对于每一个 `curr`，先找到右边第一个大于 `curr` 的位置 `nextHigher`。`curr` 能看到的人只可能在 `curr` 到 `nextHigher` 之间，范围外一定看不到。

随后尝试对这个范围内的每个数做检查：如果某个数右侧的第一个更高者位置大于 `curr`，说明它没有被遮挡，可以被 `curr` 看到；否则它被中间的人遮挡。

但这个做法最坏情况下需要对每个位置遍历后面一段范围，时间复杂度会退化到 `O(n^2)`，无法通过 `n = 10^5` 的数据范围。

之后尝试逆向复用结果，但发现不能简单继承后一个人的答案。因为前一个人能看到的数，除了末尾那个更高的阻挡者之外，其他很多都会被遮蔽，真正可复用的不是答案本身，而是“遮蔽关系”。

进一步观察后发现：对于某个 `curr`，它能看到的是右侧一条递增链，直到遇到第一个大于 `curr` 的人为止。

因此可以先构造每个位置右侧第一个更高者 `nextHigher`，然后对每个 `curr` 沿着 `nextHigher` 链往后跳。每跳到一个能看到的人，就令 `ans[curr]++`，直到遇到第一个大于 `curr` 的人。

最后意识到，这条递增链的遍历过程，本质上就是单调栈弹栈过程。于是改成从右往左维护单调栈：弹出的更矮元素都能被当前人看到；弹完后如果栈中还有元素，则当前人还能看到第一个更高的阻挡者。

最终耗时 30min 独立 AC。

## 卡点
最开始卡在如何避免对每个位置重复检查右侧范围。

直接用 `nextHigher` 限定范围虽然能解释哪些人可能被看到，但仍然需要检查范围内的元素，最坏会退化到平方复杂度。

尝试逆向复用后，也发现不能直接继承后一个位置的答案，因为可见关系会被更高的人截断，答案本身不是稳定可复用的信息。

中间一度认为沿 `nextHigher` 链的版本复杂度“不够干净”，担心多个元素重复遍历长链。但后续分析发现，这个担心不成立：沿链统计的次数等于所有可见关系的数量，而本题所有可见关系总数是 `O(n)`。

## 关键点
本题的关键观察是：

`curr` 能看到的右侧元素，是一条沿 `nextHigher` 形成的递增链，直到遇到第一个大于 `curr` 的人为止。

可以写成直观版本：

`idx = i + 1`

当 `heights[idx] < heights[i]` 时，当前人能看到 `idx`，然后跳到 `nextHigher[idx]`。

如果最后停在一个更高的人，当前人也能看到这个阻挡者一次。

这个 `nextHigher` 链版本贴合题意，可读性强，而且复杂度也是 `O(n)`。原因是：`ans[i]++` 的总次数等于所有可见关系数量，而所有可见关系总数是线性的。

最终单调栈版本只是把 `nextHigher` 链的构造和可见计数合并在了一次从右往左的弹栈过程中：

- 被弹出的更矮元素：当前人都能看到
- 弹完后剩下的栈顶：当前人能看到的第一个更高阻挡者

## 复杂度
时间复杂度：`O(n)`

每个元素最多入栈一次、出栈一次。

空间复杂度：`O(n)`

需要单调栈和答案数组。

如果使用 `nextHigher` 链版本，则还需要额外的 `nextHigher` 数组，但整体空间复杂度仍为 `O(n)`。

## 注意
这题要理解可见关系和 `nextHigher` 链之间的关系。

`nextHigher` 链版本更贴合题意，但复杂度证明需要多解释一层。

弹栈计数版本更短、更主流，摊还复杂度证明更直接，面试时优先写最终单调栈版本。
