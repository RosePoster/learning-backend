# 224. Basic Calculator

## 我的思考
本题使用递归下降 parser 处理括号表达式，并通过全局 `index` 控制当前解析位置。

最开始的实现采用三层结构，作为解法1：

- `calculate`：处理最高层表达式中的加减；
- `count`：解析一个可计算项，可能是括号表达式，也可能退化为数字；
- `s2n`：解析普通数字，并跳过数字前后的空格。

这版的核心设计是：`count` 可以退化为 `s2n`。当表达式开头或括号内出现一元 `+/-` 时，`s2n` 会在遇到符号时返回 `0`，从而将一元表达式自然转化为 `0 +/- term`。例如 `-1` 等价于 `0 - 1`，`-(1+2)` 等价于 `0 - (1+2)`。因此不需要单独处理一元运算。

三处空格处理没有强行压缩：

- `count` 开头跳过空格，用于处理类似 `"(  ("` 或 `"(  121"` 的情况；
- `count` 循环中跳过空格，用于处理类似 `")  )"` 的情况；
- `s2n` 中跳过空格，用于处理数字前后空格，例如 `"(  121  )"`。

三者语义不同，强行压缩反而可能让逻辑变乱。

后续又压缩得到相互调用结构，作为解法2：

- `calculate` 负责解析当前层表达式，遇到 `)` 或字符串结束时返回；
- `parseValue` 负责解析一个值，该值可能是数字，也可能是括号表达式；
- 如果 `parseValue` 遇到 `(`，则消费左括号并回调 `calculate` 解析括号内部表达式。

解法2 本质上是更标准的相互调用递归下降结构：`calculate` 解析表达式，`parseValue` 解析表达式中的一个值。它更紧凑，也统一了最高层和括号层的处理逻辑；但由于两个函数相互调用，阅读时需要先理解整体文法结构，因此可读性相比三层结构略有下降。

## 卡点
- 仍然存在低级失误：使用 `char c = s.charAt(index++);` 读取字符后，又额外推进了一次 `index`，导致隐蔽错误。

## 关键点
- 本题不需要显式处理一元运算：一元 `+/-` 可以统一退化为 `0 +/- value`。
- 解法1 的核心是三层结构：`calculate -> count -> s2n`，职责更细，阅读和 debug 更直接。
- 解法2 的核心是相互调用：`calculate` 解析表达式，`parseValue` 解析数字或括号表达式，更紧凑但要求函数命名和语义足够清楚。
- `index` 的语义需要保持稳定：所有解析函数都依赖全局 `index` 表示当前待处理字符。
- 括号表达式的结束由当前层 parser 消费 `)` 后返回，避免上层继续误读括号内容。

## 复杂度
- 时间：`O(n)`
- 空间：`O(depth)`，其中 `depth` 为括号嵌套深度。

## 注意
- 一元 `+/-` 不需要额外处理，通过 `s2n` 遇到符号返回 `0` 的方式自然统一为 `0 +/- term`。
- 三层结构中，`calculate` 和 `count` 都有处理加减表达式的味道，存在一定重复，但层级更显式，可读性更直接。
- 相互调用结构更紧凑，但 `s2n` 的职责已经不再只是 string to number，因此改名为 `parseValue`。
- 三处空格跳过对应的语义不同，没有强行压缩。
