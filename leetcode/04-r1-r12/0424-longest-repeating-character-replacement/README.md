# 424. Longest Repeating Character Replacement

## 我的思考
本次复刷写出了真实维护 `maxFreq` 的版本：用 `freqs` 记录字符频率，再用 `buckets` 维护不同频率下有哪些字符，从而在窗口左端收缩时让 `maxFreq` 可以真实下降。

这个方案逻辑能走通，复杂度也是 O(n)，但状态维护过重。真正更适合本题的做法是：`maxFreq` 不需要随着窗口收缩而下降，只维护历史最大值即可。

## 卡点
已经想到一个最优复杂度方案后，被当前建模锁住，没有触发“是否可以简化状态维护”的检查。

## 关键点
`maxFreq` 可以是历史最大频率，不必是真实窗口内的当前最大频率。

当 `maxFreq` 偏大时，窗口可能暂时不严格合法，但不会污染答案；它只会让窗口延迟收缩，不会制造一个超过真实最优解的答案。

## 主流解对照
主流解不维护真实 `maxFreq`，只在右端扩张时更新：

`maxFreq = max(maxFreq, ++freqs[c])`

窗口判断仍用：

`windowSize - maxFreq > k`

这样可以省掉 bucket / set 等额外状态，代码更短，bug 面更低。

## 复杂度
时间复杂度：O(n)  
空间复杂度：O(1)

## 注意
当为了维护真实最值而引入复杂数据结构时，要先问：

这个值是否必须真实回退？  
能不能只维护历史值 / 上界 / 下界？  
窗口是否必须每一步严格合法，还是只要答案不被污染即可？
